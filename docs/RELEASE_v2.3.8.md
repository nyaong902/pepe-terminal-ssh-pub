# v2.3.8

**워크스페이스를 창으로 분리해도 하던 일이 끊기지 않습니다.** 통화 중이면 통화가 유지되고, 불러둔
로그와 열어둔 문서도 그대로 살아납니다. 오래 쓰면 메모리가 계속 늘어나던 문제도 함께 잡았습니다.

## 📞 통화 중에 창을 분리해도 통화가 유지됩니다

MicroSIP / SSW 소프트폰에서 통화하다 워크스페이스를 창으로 분리하면 **통화가 전부 끊겼습니다.**
원인이 두 갈래였습니다.

| 어디서 | 무슨 일이 | |
|---|---|---|
| 원래 창 | 워크스페이스가 닫히면서 통화를 끊고 등록을 해제 | 탭을 닫을 때는 필요한 동작인데 창 분리와 구분하지 않았습니다 |
| 새 창 | 통화 중인 걸 모르고 다시 등록 | 등록 신호가 진행 중인 통화와 부딪혔습니다 |

이제 창을 옮기는 중에는 정리를 건너뛰고, 새 창은 **현재 등록·통화 상태를 물어보고 시작합니다.**
새 창에도 통화 중인 상대와 통화 시간이 그대로 보이고, 통화를 끊은 뒤 **재다이얼**도 그 번호로
동작합니다.

탭을 그냥 닫을 때는 예전처럼 통화를 끊고 등록을 해제합니다 — 그러지 않으면 화면 없는 계정이
전화선을 붙잡고 있어 다음에 같은 계정으로 걸 수 없습니다.

## 🕘 통화기록 화면이 생겼습니다

MicroSIP / SSW 소프트폰에 **통화기록** 탭이 추가됐습니다. 기록은 예전부터 쌓이고 있었는데
볼 화면이 없었습니다.

```
   이름              번호           시간
↙  07088008001      07088008001    오전 11:34:06  1:02
↗  07088008001      07088008001    2026-06-29 오후 8:12
↙  anonymous        anonymous      2026-02-25 오후 4:15
```

- 방향과 결과를 색으로 구분합니다 — 수신 응답 초록, 발신 응답 파랑, **부재중·무응답 빨강**
- 오늘 통화는 시각만, 지난 통화는 날짜와 함께 보여줍니다
- 이름은 주소록에서 번호로 찾아 붙입니다
- 행을 **두 번 클릭하면 그 번호로 발신**합니다
- 이름·번호 검색, 부재중만 보기, 기록 삭제

## 📊 CDR 로그분석 — 창을 분리해도 불러둔 로그가 유지됩니다

17MB 짜리 clog 를 불러 분석해둔 상태에서 창을 분리하면 **빈 화면으로 초기화됐습니다.** 이제 원문과
결과, 파일명, 보고 있던 탭이 그대로 복원됩니다.

큰 원문은 창 사이로 옮기는 방식을 따로 두었습니다 — 워크스페이스 상태에 그대로 실으면 17MB 를
두 번 복사하게 되어 창 이동 자체가 멈춥니다.

## 📄 오피스 — 확장 프로그램 팝업이 사라졌습니다

문서를 열 때 **"확장 프로그램 필요"** 창이 뜨고, 그 안의 "확장 프로그램 설치" 를 눌러도 아무 일도
일어나지 않았습니다. 이 앱에는 크롬 웹스토어가 없어 애초에 설치할 수단이 없었습니다.

확장이 필요하지도 않습니다 — 문서를 앱이 직접 넘겨주기 때문입니다. 편집기가 그 경로로 바로 열도록
바꿔서 **창이 아예 뜨지 않습니다.**

**창을 분리하면 열어둔 문서를 다시 열어줍니다.** 예전에는 빈 편집기가 떴습니다. 저장하지 않은
편집 내용은 옮길 수 없으니, 창을 옮기기 전에 저장하세요.

## 🧠 워크스페이스를 닫으면 메모리가 돌아옵니다

**"시작할 때 600MB 였다가 오피스를 쓰면 2.6GB 까지 오르고, 워크스페이스를 닫아도 줄지 않는다"** 는
제보에서 시작한 작업입니다. 무거운 워크스페이스들이 모두 앱 본체와 **같은 프로세스**에서 돌고 있던
것이 원인이었습니다. 한 번 커진 메모리는 그 프로세스가 사는 동안 운영체제로 돌아가지 않기 때문에,
화면을 닫아도 수치가 그대로였습니다.

무거운 것들을 **각자 별도 프로세스로 분리**했습니다. 이제 워크스페이스를 닫으면 그 프로세스가
종료되면서 메모리가 통째로 회수됩니다.

| 분리한 것 | |
|---|---|
| 워드·엑셀·PPT | 문서를 열 때마다 쓰던 변환 엔진이 앱 본체에 쌓였습니다 |
| 한글(HWP) | 편집기 전체가 앱 본체에서 돌았습니다 |
| draw.io 플로우차트 | 같은 문제였습니다 |
| PDF | 문서 데이터(수백 MB)가 앱 본체에 얹혔습니다 |
| 대화 아카이브 검색 모델 | 검색 한 번에 250MB 가 영구히 얹혔습니다(모델 130MB + 실행 메모리) |

브라우저 워크스페이스는 이미 별도 프로세스였는데도 여닫기를 반복하면 메모리가 계단식으로 올라갔습니다.
**여닫을 때마다 브라우저 세션이 하나씩 영구히 쌓이고 있었습니다.** 이제 세션을 재사용해서, 닫은 상태의
총량이 사이클마다 오르지 않고 **내려갑니다**(실측 1069 → 961MB).

페이지가 소리를 내면 뜨는 **오디오 서비스 프로세스(100MB 대)** 도 닫을 때 함께 정리합니다. 다른 곳에서
소리가 나는 중이면 건드리지 않습니다.

> 그래픽 프로세스가 붙잡는 메모리는 천천히 줄어듭니다 — 브라우저 엔진이 화면 캐시를 압박이 있을 때
> 정리하는 정책이라 앱에서 손댈 수 없는 부분입니다.

부수 효과로 **앱 실행 파일이 가벼워졌습니다** — PDF 엔진이 앱 본체 묶음에서 빠져 3.88MB → 3.20MB.

## 🔎 대화 아카이브 검색 — 요약이 끊기지 않고, 비용은 1/4

**요약이 중간에 잘려 나오지 않던 문제**를 고쳤습니다. 응답을 60초까지만 기다리다 프로세스를
끊었는데, 실제로는 107초가 걸리는 경우가 있었습니다. 이제 응답이 오는 동안에는 기다립니다.

같은 검색의 비용이 **$1.47 → $0.33** 으로 줄었습니다. 발췌문을 만들 때 같은 대화가 여러 번 중복돼
들어가고 있었습니다 — 프롬프트의 3/4 가 반복이었습니다. 중복만 걷어냈고 찾아주는 내용은 그대로입니다.

검색 화면에 두 가지 손잡이가 생겼습니다.

- **요약 모델** — 기본 / Opus / Sonnet / Haiku. 아래로 갈수록 저렴합니다
- **사고 예산** — 요약 전에 생각하는 양의 상한(기본 1500). 줄이면 더 싸고 빠릅니다

## ⌨ 모든 입력창에서 Ctrl+U

터미널에서 Ctrl+U 로 입력한 줄을 지우던 것처럼, **일괄전송 바·검색창·세션 편집기 등 모든 입력창**
에서도 같은 동작이 됩니다. 옵션 > 단축키에서 다른 키로 바꿀 수 있습니다.

터미널에서는 예전처럼 셸로 그대로 전달됩니다.
